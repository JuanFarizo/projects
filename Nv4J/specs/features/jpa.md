Known limits of R2 (said plainly): an entity that extends a library class (`AbstractPersistable<Long>`) is not judged; derived methods of repositories declared with `@RepositoryDefinition` are not found (only `extends ...Repository<T, ID>`); Spring's custom-fragment methods and `@Query`-less methods named on purpose for a fragment would be flagged (`findByNonsense` implemented by a fragment); property names with `@Column(name=)` differences do not matter (Java names are used, like Spring).

Oracle for R2 (to do with the live run): Spring Data itself rejects a bad derived name when `spring-boot:process-aot` runs on `jpa4`. The live check puts every name of check 76's list into a repository of the fixture, runs `process-aot` (must succeed) and then the bad names (must fail naming each property), so the parser is compared with the real implementation and not only with my reading of it.

## Check 82 hang (root cause, 2026-11-24) and the real defect behind it

Symptom: `82_jpa4_spring` printed `no_aot_lens` and `aot_command` PASS and never finished (20+ minutes) on Mason 2.2.0 and on the 2.5 pre-release.

- Evidence: `jstack` of the Spring LS during the hang showed a pool thread at 70 to 90 % CPU in `DataRepositoryAotMetadataCodeLensProvider.provideCodeLenses` (one AST walk per request) and `/tmp/nv4j/logs/spring-boot-ls.log` filled with `CancellationException` (1530 in 3 minutes). mvn was NOT alive (the build ended with exit 0 and the JSON existed). An instrumented copy of the check (`/tmp/nv4j/logs/a1e64-82-hang-trace.txt`, 1.8 million lines) showed the loop: `textDocument/codeLens` answered in under 1 ms with 4 lenses, the predicate was false, and the next request followed at once, about 3600 requests per second for 165 s, past the 60 s timeout.
- Root cause (the check, not the product): `lenses_with` used `vim.wait(timeout, fn, 1500)` where `fn` calls `client:request_sync` (itself a `vim.wait`). In Neovim 0.12.6 an outer `vim.wait` whose predicate runs a nested wait never checks its deadline or its interval: the predicate runs in a hot loop forever. Pure reproduction, no LSP: 2,107,234 calls in 1.5 s for a 300 ms wait (check `121_poll_deadline`, case `nested_wait_ignores_deadline`). Only check 82 had the pattern (grep of all checks and `nvim/lua`: the product never nests a `request_sync` in a `vim.wait` predicate).
- Fix: `lsp.poll(timeout_ms, interval_ms, fn)` in `tests/lib/lsp.lua` (hard deadline on `hrtime`, plain `vim.wait(interval)` between calls); check 82 uses it. Control `121_poll_deadline` (3 cases): the plain pattern is unbounded here, `lsp.poll` returns nil after 501 ms, returns the value as soon as it is truthy. The case `nested_wait_ignores_deadline` will FAIL on a Neovim that fixes the behaviour; then `lsp.poll` can go back to `vim.wait`.
- Behind the hang there was a real product defect. With the loop bounded, the check ran to the end with `DONE 82_jpa4_spring 5 3` (`neg-a1e64-82-no-notify-20261124.log`): after `aot_command` the lens stayed "Show AOT-generated Implementation, Query, etc..." for 45 s. The Spring LS reads the AOT JSON through file-change events (VS Code's watcher sends them). Neovim's watcher does not see files in a `target/spring-aot` folder that did not exist when the server registered its watchers. One `workspace/didChangeWatchedFiles` (type Created, the JSON path) made the lens switch within 1.5 s; `java/projectConfigurationUpdate` was not needed. Fix: `nv4j.aot.notify_files(dir)` sends that notification for every JSON under `target/spring-aot` and `build/generated/aotResources` after a successful build, before the lenses are asked for again.
- Result: `82_jpa4_spring` 8 cases, `DONE 82_jpa4_spring 8 0` three times in a row through `tests/run.sh` on Mason 2.2.0 (`test-20261124-085239.log`, `-085259.log`, `-085321.log`; about 20 s each) and once more on 2.5.2026111900. Without the notification (control) it is 5/3 (`lens_query`, `add_query_offered`, `add_query_applied` FAIL).
- 2.5 difference found while doing this: on an `@Query` method 2.5 offers one more code action, "Convert query to text block". `add_query_offered` now counts only "Add `@Query`" actions.

# Feature: JDK selection and Java 25 correctness

Priority: P1. Status: done (Task 4). Tests: `tests/checks/20_java25.lua`.

## How JDTLS picks JVMs (two independent choices)

1. The JVM jdtls itself runs on. The Mason `jdtls` wrapper (`packages/jdtls/bin/jdtls.py`) uses `--java-executable=<path>` if given, else `$JAVA_HOME/bin/java` if that file exists, else `java` from PATH. It refuses Java < 21 only (`--validate-java-version`), which is not enough: Mason jdtls 1.63.0 needs JDK >= 25 (its bundles require `osgi.ee JavaSE 25`; on 21 to 24 it exits with code 13, seen with `JAVA_HOME` = 23 or 24, 2026-11-16). The number is the constant `nv4j.jdk.SERVER_MIN_JAVA`; to measure it again read the `Unresolved requirement ... (version=NN)` lines in `~/.cache/nv4j/jdtls-config/<project>-<hash>/*.log`. `--jvm-arg=...` only adds JVM options. Without our fix the server ran on whatever PATH had: with JDK 21 first, jdtls exited with code 13 on this project (red baseline of check 20, see trial log).
2. The JVM used to compile each project. jdtls (jdt.ls) maps `java.configuration.runtimes` (list of `{name="JavaSE-N", path, default}`) to Eclipse execution environments. A Maven project's `release`/`source` is matched to the runtime with that name; the `default` one is used when nothing matches. `java.jdt.ls.java.home` is a legacy alias of choice 1 and is not needed because we pass `--java-executable`.

## How IntelliJ does it

Not verified from source. The local clone `~/.cache/nv4j/intellij-community` is sparse (about 1900 files, only parts of `java/` and `platform/`), and it contains none of `JavaHomeFinder`, `ProjectJdkTable`, `ProjectRootManager`, `LanguageLevelProjectExtension` or Maven importer code (searched by file name). What is stated here is general product behaviour, not sourced: IntelliJ keeps a Project SDK and a language level as separate settings, fills its SDK table by detecting installed JDKs, and the Maven import sets the language level from the pom. nv4j copies that idea only: discover all JDKs, register all, pick the default from the build file.

## Ruling (user, supersedes the brief)

Nothing is pinned to Corretto 25: the user switches JDKs with SDKMAN (lazily loaded, so `java` and `JAVA_HOME` are unreliable in a spawned nvim).

- `require("nv4j.jdk").discover()`: scans in order `$SDKMAN_DIR/candidates/java/*` (default `~/.sdkman`, skipping the `current` link), `~/Library/Java/JavaVirtualMachines/*/Contents/Home`, `/Library/Java/JavaVirtualMachines/*/Contents/Home`. Versions come from each home's `release` file (`JAVA_VERSION`), never from running `java`. `NV4J_JDK_ROOT` (":"-separated) replaces the scan list, tests only.
- More places (2026-11-23, after IntelliJ `JavaHomeFinderBasic`: `findSdkManCandidatesDir`, `findMiseInstallsDir`, `findAsdfInstallsDir`, `findJavaInstalledByJabba/Gradle`, and `JavaHomeFinder.DEFAULT_JAVA_LINUX_PATHS`): `roots()` now lists, in this order, SDKMAN (`$SDKMAN_CANDIDATES_DIR/java`, else `$SDKMAN_DIR/candidates/java`, else `~/.sdkman/candidates/java`; the first one that is set wins), the two macOS dirs, mise (`$MISE_DATA_DIR/installs/java`, else `$XDG_DATA_HOME/mise/installs/java`, else `~/.local/share/mise/installs/java`), asdf (`$ASDF_DATA_DIR/installs/java`, else `~/.asdf/installs/java`), jabba (`~/.jabba/jdk`), Gradle toolchains (`~/.gradle/jdks`, whose homes sit one folder down, so each child that is not a JDK is searched one level deeper) and `/usr/lib/jvm`. Duplicates are removed by real path, the first root's spelling wins (a mise `21` link to `21.0.1`, `/usr/lib/jvm/default-java`). A home without `bin/javac` (a headless JRE, e.g. Ubuntu's `openjdk-25-jre-headless`) sorts after every full JDK, so it never beats a JDK as "newest" or as the project runtime; `tests/lib/jdk_home.lua` skips it (it needs a compiler). `roots()` only builds strings: nothing touches the disk until the first `discover()` (case `zero_cost_startup`). Version choice (`.sdkmanrc`, pom, `$JAVA_HOME`, newest) is unchanged and works on the new homes (case `selection`). Not copied from IntelliJ: PATH scan, `JAVA_HOME` scan beyond what was there, Windows/WSL/Homebrew finders. Check `111_jdk_roots` (17 cases, pure), controls `tests/lib/control_111.sh` (9 patches).
- `.server_home()` (ruling revised 2026-11-16: the old ">= 21" was wrong for jdtls 1.63.0): `$JAVA_HOME` if it is a valid JDK >= `SERVER_MIN_JAVA` (25), else the newest non-EA discovered one >= 25, else a clear error (needs JDK >= 25, lists the installed JDKs, says the project JDK can stay 21/23 because it is a separate choice, suggests `sdk install java 25-amzn`). With SDKMAN `sdk use java 23.0.2-amzn` for a Java 23 project, jdt.ls still runs on the newest 25 and the project keeps JDK 23 (`.runtimes`). When jdt.ls exits with code 13 a notification says which JDK it ran on and that it needs >= 25 (`plugins/java.lua` on_exit); `:Nv4JHealth` reports an ERROR when no JDK >= 25 exists. The result goes into `--java-executable=` and `cmd_env.JAVA_HOME`.
- `.runtimes(root)`: one `JavaSE-<n>` per major >= 8 (8 is `JavaSE-1.8`), preferring `$JAVA_HOME`'s then SDKMAN `current`'s JDK for its major, else the newest. `default=true` goes to the first match of: `.sdkmanrc` `java=` major (only if that major is installed, else falls through), pom `maven.compiler.release`, `java.version`, `maven.compiler.source` (plugin-level `<release>`/`<source>`/`<target>` and `maven.compiler.target` too; `${prop}` resolved up to 5 deep), `$JAVA_HOME` major, newest. Limit: only the project's own pom and `.sdkmanrc` are read. A `java.version`/release inherited from a parent pom (other than the Spring Boot starter parent, whose child pom normally sets `java.version` itself) is not seen and falls through to `$JAVA_HOME`/newest. JDKs without a `release` file (SDKMAN 8.x) get their major from the directory name; `$JAVA_HOME`'s JDK is registered even outside the scan roots; early-access builds are skipped when choosing "newest".
- Set per project in `opts.jdtls` as a function (LazyVim passes it the built config, so `root_dir` is known).
- `java25()` was dropped; nothing needs it.
- jdtls `-configuration` moved to `/tmp/nv4j/jdtls-config/<project>` (`paths.lua`); since the final review it lives in `~/.cache/nv4j/jdtls-config/<project>` with the workspace (`~/.cache/nv4j/jdtls-data`), because macOS empties `/tmp`. Equinox creates it itself; the shared config stays read-only in Mason. The base dirs are re-created on every start by `paths.lua`.

## Test design

`tests/run.sh` scrubs `JAVA_HOME` and puts a JDK of `NV4J_PATH_JDK` (default 21) first on PATH; `mvn compile` of the fixture alone gets JAVA_HOME=JDK 25 in its own environment. Check 20 asserts (case 1, fixture release 25): zero errors on `Modern.java`, jdtls reports source/compliance/target 25 and a JDK 25 `vm.location` (via `java.project.getSettings`), and the server process's `java` is `server_home()` and is not PATH's 21. Case 2: a temp Maven project (release 21, sealed/records/pattern switch) under `/tmp/nv4j/proj21` reports 21 and a JDK 21 location with zero errors. Case 0 (2026-11-16, pure, `NV4J_JDK_ROOT` stubs): `JAVA_HOME` 23 and 24 fall through to the newest >= 25, 25 is kept, only 21 and 23 installed gives the error text, health reports an ERROR. Check `21_server_jdk` (live): `tests/run.sh` starts nvim with `JAVA_HOME` = a real JDK 23, a temp Maven project attaches, and the server process runs on JDK 25. Control `tests/lib/control_20.sh` (the old ">= 21" rule): the four cases fail.

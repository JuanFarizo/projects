# Library navigation: sources, Fernflower, CFR backup

Go to definition (`gd`) into a class of a jar. What you see depends on what is on disk; nothing is configured per project. Code: `nvim/lua/nv4j/decompile.lua` (CFR backup, loaded on the first `jdt://` buffer, never at startup), `nvim/lua/plugins/java.lua` (the two `downloadSources` settings and the `open_classfile` wrapper), `nvim/lua/config/keymaps.lua` (`:Nv4JDecompile`, `:Nv4JInstallCfr`). Research: `docs/RESEARCH-decompiler.md`. Check: `tests/checks/95_library_nav.lua` (19 cases), controls `tests/lib/control_95.sh`.

## Settings sent to jdt.ls (verified in jdt.ls 1.63.0 bytecode, `docs/RESEARCH-decompiler.md`)

- A Maven project already fetches a missing `-sources.jar` LAZILY, on navigation, with no setting: `SourceContentProvider.getSource` -> `MavenBuildSupport.discoverSource` -> `MavenSourceDownloader` identifies the artifact (`META-INF/maven` properties, else Maven Central by SHA-1, else the local repository layout), schedules m2e's download job for that one jar and waits up to 3 s (`MAX_TIME_MILLIS`), one request per jar per hour (`downloadRequestsCache`). The first open shows Fernflower when the download takes longer; the next open shows the sources once m2e attached them. Offline (`java.import.maven.offline.enabled`, or no network) the request fails and Fernflower stays; the check forces offline mode and both cases open in well under the 20 s budget.
- `java.eclipse.downloadSources = true` (Nv4J sets it): the same lazy path for Eclipse `.project` projects (`EclipseBuildSupport.discoverSource` is gated by it; the loose-file default project already had it). No startup or idle cost: it is read only inside `discoverSource`.
- `java.maven.downloadSources` is NOT lazy: `MavenProjectImporter.importToWorkspace` copies it into m2e (`MavenConfigurationImpl.setDownloadSources`) and m2e's `BuildPathManager.configureAttachedSourcesAndJavadoc` then schedules a download for EVERY classpath entry without sources, 1 s after each classpath configuration (import, pom change). That is network and job time during import, for every library you never open, and on a corporate Nexus or offline a failed resolution per jar. It stays off (`false`). Owner's decision asked for `true`; the performance requirement in the same decision (no startup or idle cost) is why it is not: set `vim.g.nv4j_maven_download_sources = true` in `nvim/lua/config/options.lua` to get the eager download. Not measured online (no download was made in this work): the eager cost is read from the bytecode, not timed.

## CFR backup

- One pinned release, `org.benf:cfr:0.152` from Maven Central (the newest version listed in its `maven-metadata.xml`, 2021-12), licence MIT (its POM, `<license><name>MIT</name>`), jar 2,162,315 bytes. The constant `M.CFR` in `nvim/lua/nv4j/decompile.lua` holds version, URL and SHA-256 `f686e8f3ded377d7bc87d216a90e9e9512df4156e75b06c655a16648ae8765b2` (the `cfr-0.152.jar.sha256` Maven Central publishes; a fresh download matched it and the `.sha1` `48ef4892cfe8feffddbbd0ff077735140557db74`).
- Where: `~/.local/share/nv4j/nv4j/tools/cfr-0.152.jar` (`stdpath("data")/nv4j/tools`, next to Mason's dir). Installed by `:Nv4JInstallCfr`, or by itself the first time CFR is needed and the jar is missing: one `curl` in the background, SHA-256 checked before the file is kept, one warning if it fails, no retry in that session (the next session tries once more). Nothing at startup: the command is one `nvim_create_user_command`, the module loads on the first `jdt://` buffer (`zero_cost_startup`, `zero_cost_open`).
- How it runs: never inside jdt.ls (no bundle, nothing on its classpath). A separate `java -jar cfr.jar <jar> --jarfilter '^<class>(\$.*)?$' --silent true` on the JDK jdt.ls runs on (`nv4j.jdk.server_home`, never `PATH`), `vim.system` with a 20 s timeout, output cached in memory per `jar!class` for the session (second use of the same class spawns nothing). The jar and the class name come out of the `jdt://` URI (no jdt.ls request, no network). A missing jar warns once and spawns nothing.
- Trigger: after nvim-jdtls filled a `jdt://` buffer (wrapper around `jdtls.open_classfile`), when the content has no non-blank line, or any line contains `// $FF: Couldn't be decompiled` (what Fernflower 253.x writes as the body of a method it gave up on; jdt.ls only logs "Line mappings not available ... decompilation may have failed"; a Fernflower exception makes `DecompilerImpl` return null and `ContentProviderManager` the empty string, so the buffer is empty). A normal Fernflower buffer or real sources are never replaced (`trigger_normal_kept`, `fernflower`).
- Force or compare: `:Nv4JDecompile cfr` on any `jdt://` buffer replaces it with CFR (`// Decompiled with CFR 0.152 (on demand)`), `:Nv4JDecompile fernflower` asks jdt.ls again (its content cache answers at once) and puts Fernflower or the sources back.
- Upgrade: change `version`, `url` and `sha256` in `M.CFR` (take the `.sha256` file next to the new jar on `repo1.maven.org/maven2/org/benf/cfr/<version>/`), delete the old jar from the tools dir, `:Nv4JInstallCfr`. Nothing else names the version.

## Limits

- CFR's `--jarfilter` runs over the whole jar's class list to find the matches (fast: 0.3 s on commons-codec, see `cfr_live`), and the class is decompiled with the jar as its only classpath: types from other jars show as `Could not load the following classes` in CFR's header comment and are still named correctly.
- No CFR for JDK module classes (`jrt:`): not in a jar.
- The `$FF` trigger replaces the WHOLE class, also the methods Fernflower did decompile; `:Nv4JDecompile fernflower` brings them back.
- Line numbers of decompiled code (either decompiler) do not match stack traces or the debugger; sources jars do.
- The eager `java.maven.downloadSources` was not timed online; the lazy fetch was not exercised online either (no download in this work): both come from reading the bytecode.
